# Private runtime binding

The reviewed workflow source enables execution after exact owner/manual-main/first-attempt identity checks. Source enablement is not evidence of a production run. Every dispatch still requires the approved exact source, private receipt and operation scope; this document grants no additional authority. Local verification used no production calls.

## Composition

`scripts/run_private_authority_route.py` provides a single-process binding for the two existing coordinators. Its only command-line inputs are the closed route, public reviewed Compute SHA and opaque receipt commitment. The Store token and provider key are supplied by the future approved hosted caller through its existing secret environment. Exact private pins, approval bytes and digests are passed in memory, never public command arguments, workflow outputs, summaries or artifacts.

The wrapper:

1. Checks the existing owner/manual-main/first-attempt platform fields, source SHA syntax, commitment syntax and credential shape before private access. These comparisons do not attest that an arbitrary local environment is genuine GitHub context.
2. Resolves its own Compute source location, verifies exact HEAD and clean tracked/index/untracked/ignored contents, rejects replacement refs, grafts, shallow history and alternates, and allows only a small ordinary local Git configuration set. In particular, local includes, URL rewrites, alternate push URLs, executable filters and credential settings are rejected. Origin must be exactly `https://github.com/yuatom/stock-market-data` (with optional `.git` suffix), and the independently read remote main must equal the reviewed SHA.
3. Calls the separate write-capable promotion preparation: quiet receipt lookup, independent public commitment verification, private identity, fresh private Store fetch and strict descriptor/authority selection. If main is the authority’s exact sole parent, it promotes only that approved one-addition commit under the existing hosted collector lock using one explicit exact-head lease. If main already equals the approved authority it does not write again. Any other head stops. The old read-only materializer and preflight APIs remain read-only. Credential possession or a selected descriptor is not consent.
4. Repeats Compute verification. Only after the selector returns does it temporarily install child-process Git authentication. It then verifies the fresh Store origin and push destination, clean HEAD, and exact remote main plus deterministic descriptor ref immediately before entering the coordinator.
5. Calls `run_soxx_capture.execute` with the selected private authority head/digest and the existing private metadata check, helpers and configuration, or calls `run_eleven_symbol_append.run_official` with the selected canonical approval bytes/digest. It never overrides the official append surface guard, provider transport, clocks, retention or publication implementation. Request identity is the actual first-attempt run ID, `<GITHUB_RUN_ID>-1`.
6. Leaves approval-window, request/credit caps, create-only claim, durable debit, provider guard, retention, conditional append and uncertain-publication handling to those unchanged coordinators. SOXX success means retained unqualified evidence, not market qualification. Any non-complete append result is a stop. The wrapper returns/prints only `PRIVATE_ROUTE_COMPLETE` or `PRIVATE_ROUTE_STOPPED_INSPECT_BEFORE_RETRY` and never returns private coordinator result data.

Beyond the specifically approved authority promotion, the wrapper does not make independent Store changes. It never retries a coordinator, provider request or uncertain write, and never refunds, repairs, reuses a failed directory or renews a grant. Existing bounded verifier read retries remain unchanged. The fresh temporary parent and Store checkout are private mode-0700 directories. Uncertain-run data is left for authorized private inspection, not uploaded as a debugging artifact.

## Transient Git authentication

The materializer intentionally stores no credential. The wrapper supplies a Basic Authorization header through child environment configuration scoped to the **exact Store HTTPS repository URL** ending in `.git`, not the GitHub host. Real Git URL-matching tests verify that it does not match Compute, another repository or another host. Redirects, proxies, credential helpers and non-HTTPS transports are disabled, TLS verification stays enabled, and hooks/fsmonitor are disabled. System/global Git configuration is excluded. No authentication header is persisted in repository config or put into argv.

The complete inherited process environment is replaced by an allowlisted environment while running. Provider key and Store token are passed to the coordinators explicitly and are not exported to ordinary Git subprocesses as secret-named environment variables. Git trace, ambient proxy and Git override settings are absent. Authentication is activated only after strict authority selection because that reader correctly rejects ambient `GIT_CONFIG_*` overrides. Publication-verifier subprocesses inherit the transient authentication settings they need. The append coordinator’s verifier launcher preserves validated inherited Git config entries, then appends hooks/fsmonitor restrictions instead of replacing the existing entry count. A real child-process test and a full synthetic eleven-symbol coordinator/verifier-chain test cover this boundary. Environment, import path and bytecode settings are restored on success or failure.

Python output and file descriptors 1 and 2 are redirected to the null device throughout private execution, including inherited child output. Exceptions are collapsed into a value-free stop with no exception context. This is an accidental-output boundary, not protection against a malicious dependency, debugger, hostile runner administrator or deliberately exfiltrating reviewed source.

## Hosted deployment requirements

No environment variable such as `AUTHORIZED=true` or `LOCK_HELD=true` can grant permission or prove locking. Every enabled workflow invocation must retain the reviewed workflow change and all of the following:

- Keep owner-only manual-main first-attempt dispatch checks ahead of all private credentials and reads. Bind each workflow to its fixed route; do not expose a route selector that can switch coordinators.
- Use the exact approved Compute source SHA, checked out in a fresh trusted runner checkout with `persist-credentials: false`, full history and no reused workspace, mutable modules or unreviewed import hooks. Invoke a fresh Python process with `-B` (or `PYTHONDONTWRITEBYTECODE=1`) from that checkout. Avoid test/cache files inside it: the source check intentionally rejects even ignored untracked files. Any dependency install must be separately reviewed and pinned, outside the source checkout.
- Preserve the existing same-repository `market-data-collector` concurrency group, `cancel-in-progress: false` and queue behavior across **every** collector/route that writes this Store. Hold that lock for the entire private materialization, coordinator, retention and publication sequence, not just a preflight job. The Python wrapper cannot verify GitHub scheduler ownership. Cross-repository writers require separate exclusion; this design does not pretend that a local lock would cover them.
- Source the opaque expected commitment from the independently authorized owner dispatch, never from the fetched sidecar. Verify approved immutable creation/readback of exact private runtime authority, descriptor and sidecar before dispatch. Their Git identities must remain private. An occupied ref must not be replaced; a new nonce cannot revive a consumed approval.
- Preserve existing minimum permissions and existing credential names. Do not introduce broader permissions, persistent credentials, new secrets, debug shell tracing, log export, artifact upload, or public private-pin inputs.
- Ensure runner timeout, disk capacity and credential lifetime cover the approved operation. The wrapper does not bound fetched history size or provide an external global deadline beyond coordinator deadlines and bounded Git operations. Review the current short preflight-only workflow timeout before binding an actual coordinator.
- On cancellation, unknown provider outcome, changed remote head, failed publication, or a stop status, inspect existing private evidence under the original grant. Never automatically dispatch again, refresh the approval, repair refs or retry HTTP.

The execution command has the form `python -B -m scripts.run_private_authority_route --route <workflow-fixed-route> --compute-sha <public-approved-sha> --receipt-commitment <public-approved-commitment>`. Both workflows include that command after the exact public-context identity step, with exact source checkout, persistent credentials disabled, Python bytecode disabled, and pinned PyYAML 6.0.3. Failed identity checks stop before checkout or secret access.

## Exact approved operation scope

The consolidated operation must name the final reviewed source/merge and workflow activation; exact private authority, descriptor and receipt creation destinations; independent readback; specific SOXX one-request/one-credit evidence-only scope and eleven-symbol at-most-eleven-request/eleven-credit conditional-append scope; validity window; private retention destination; market-fact change limits; and one-shot execution with no automatic retries. No local test or valid commitment substitutes for that approval.

## Verification boundary

Focused tests use synthetic Git repositories and fake tokens. They verify both coordinator argument mappings, fail-closed source/origin/config/index checks, remote source/ref changes, private stdout/stderr suppression, URL-scoped ephemeral authentication, cleanup after exceptions, fixed public CLI messages and no retries. Private fetches, provider calls and remote operations are replaced at their boundaries. Existing unchanged coordinator tests separately exercise accounting/claims/provider/publication behavior. This is preproduction verification, not evidence that real secrets are configured, platform locks are held, production heads match or a live capture succeeded.


## Locked off-main authority promotion

`scripts/private_authority_promotion.py` is a separate, explicitly write-capable module. It must run within the same genuinely held hosted collector concurrency lock as the coordinator. There is no `LOCK_HELD` flag and no local substitute for the scheduler’s lock. The reviewed identity-guarded workflow remains the only intended production caller.

Future authorized preparation creates the runtime authority, descriptor and private receipt **off main**. Use the existing connector’s create-only `create_branch` with each explicitly approved exact starting SHA, then only the approved file additions on those preparation branches. Deterministic descriptor and receipt pointers are ordinary private `refs/heads/capture-authority/<route>/<compute-sha>` and `refs/heads/capture-receipts/<route>/<compute-sha>` branches. An occupied branch is a stop: never overwrite, move, delete or reuse it to retry. Independently read back exact commits, trees and file identities. These instructions grant no independent creation authority; exact destinations and additions must match the scoped grant.

Inside the lock, the new module fetches current main and descriptor ancestry into a new mode-0700 directory. It moves **only local main** to the receipt-bound authority and invokes the existing strict selector before any remote write. That selector proves the authority’s literal single parent and sole normal-file addition, plus the descriptor’s exact single-parent/single-addition graph and canonical private approval. If observed remote main differs from both that literal baseline parent and the exact authority, the module stops. It never adopts an unrelated descendant.

The selected approval must be within its UTC validity interval and match the current New York execution day. These checks run before source revalidation and again immediately before promotion. The mandatory callback rechecks exact reviewed Compute checkout and remote main. The module rechecks descriptor/main, then makes at most one promotion using an explicit main-head lease. This is a proved one-addition fast-forward, not permission to rewrite history. A separate post-push remote read and fetch verifies main, descriptor and immutable objects before strict selection runs again. A failed/unknown push acknowledgement or readback stops without another push, rollback, coordinator call or automatic repair, even when the first push actually succeeded.

Configured historical-cutoff maturity remains **coordinator-only**: promotion does not authorize an immature provider request. The exact requested cutoff must be earlier than the current ET accounting date and mature at the configured time (currently 07:00 ET) on the calendar day after that cutoff. Older completed data need not wait for today’s 07:00. The current ET accounting date, 200/day and 8/minute limits, expiry and all claim/debit/provider checks remain unchanged. Both routes recheck cutoff maturity and grant freshness immediately before HTTP, then bind that same final UTC timestamp to the confirmed debit minute and the strict before-:58 boundary, with no slow Git operation afterward. Authority-write permission remains distinct from provider execution permission.

Synthetic tests cover both routes against real local bare remotes, successful one-addition promotion, already-current authority without a write, stale main, moved descriptor, invalid immutable graph, source failure or drift, expiry during revalidation, explicit lease races, rejected/unknown push outcomes, and failed post-push readback. They assert the difference between pre-push failure (no remote write) and post-push uncertainty (possible committed authority left untouched), while the public error remains constant. Network authentication is supplied only to network subprocesses; the strict local selector never receives ambient authentication overrides.


## Logical inclusive cutoff versus provider wire boundary

The two hosted routes interpret the approved `end_date` as an inclusive daily-session cutoff. A date-only provider upper bound can exclude that session; Twelve Data’s [historical-data documentation](https://support.twelvedata.com/en/articles/5214728-getting-historical-data) illustrates this boundary behavior. The hosted transports now encode the same approved date as `YYYY-MM-DD 23:59:59`. They do not request a next-day upper bound, change the approved start date/output size, or widen accepted response dates.

`scripts/inclusive_daily_wire.py` supplies the shared secret-free mapping. Official SOXX capture opts into it explicitly; unrelated callers of the generic capture function retain their previous default behavior. The eleven-symbol transport uses the same mapping. Approval bytes, `request.json`, and logical envelope/request identities remain date-based and unchanged. Both routes retain the sanitized endpoint and mapped query parameters under `wire_request` in the existing private `attempt.json`, marked as a `provider_wire_request_plan` with the credential omitted. This is pre-request intent, not proof that HTTP occurred. No API key, credential-bearing URL, or new public output is recorded.

Raw-response validation remains bounded by the exact logical dates, including rejection of a next-day row. The mapping does not add requests, credits, retries or evidence writes. A consumed SOXX or append grant stays consumed; fixing transport semantics does not authorize a retry or renew any approval.
