# Private authority receipt commitment: deployment-gated implementation

This candidate does not activate, dispatch, publish, create a reference, read production data, provision credentials, or change workflow gates. `scripts/private_authority_receipt.py` exposes pure canonicalization, validation, commitment and verification functions only. It has no CLI or execution wiring. Publishing even the opaque commitment requires later explicit approval of this exact disclosure and the concrete operation. No such approval is inferred here.

## Protocol and ordering (implemented readers, gated execution)

1. Finalize and independently review the Compute source SHA first. Its public workflow must retain all existing identity, concurrency and runtime gates when any future separately reviewed binding is approved.
2. With explicit authorization, create the exact private runtime authority and descriptor. Preserve the descriptor's single-parent, single-added-file shape: only `capture-authority/selection.json` atop the exact authority Store head, off main. Independently read back the exact authorized creation; do not adopt whatever an existing mutable ref contains.
3. A trusted creator makes a receipt with exactly `schema_version` (integer 1), `kind` (`capture_authority_receipt`), one of the two closed `route` names, `compute_sha`, `authority_store_sha`, `descriptor_commit` (each lowercase 40-character Git SHA-1), and `nonce` (64 lowercase hexadecimal characters encoding 32 fresh cryptographically random bytes from an OS-backed CSPRNG). A nonce must not be a timestamp, request ID, deterministic hash, password or reused randomness. The validator can check encoding and reject an all-zero unset sentinel, but cannot prove entropy or uniqueness.
4. Receipt encoding is ASCII JSON, sorted keys, no spaces, no ASCII escaping alternatives, and exactly one final newline. Parsing rejects duplicate/extra/missing keys, non-finite numbers, noncanonical bytes, wrong types, and payloads larger than 2,048 bytes. The public commitment is lowercase hex SHA-256 of the literal bytes `private-authority-receipt:v1`, then a NUL byte, then the complete canonical receipt bytes including final newline.
5. Store/deliver the receipt through a separately authorized **private sidecar object/reference**, not inside the descriptor commit it names and never in the descriptor's tree. The quiet reader implements deterministic lookup, bounds and commitment validation. Sidecar creation, private readback and retention still need a specifically authorized execution plan. The module writes nothing. Do not add a second file to the descriptor or put a receipt atop Store main.
6. Only after the final Compute SHA and descriptor commit exist can the receipt and its commitment be made. The gated workflow dispatch interface carries the commitment alongside the already public reviewed Compute SHA. Never insert this receipt-dependent digest into that same Compute source commit: doing so changes its SHA and creates a hash cycle. Never insert the receipt into its own named descriptor commit either.
7. A future trusted caller checks the owner manual-main first-attempt dispatch identity, exact reviewed Compute source and workflow route. It obtains the private receipt through the reviewed sidecar delivery and checks the public commitment plus independent route/source expectations. Then its exact pins feed the existing quiet metadata/object readers and strict local authority selector. Private values must remain in private memory/quiet storage, never public workflow command text, command echoes, logs, step outputs, summaries, artifacts or exception diagnostics. Trusted quiet local Git subprocess argv can contain object pins; credentials are never placed in argv. All remote main/ref checks and runtime gates still apply.

## Exact disclosure requiring later approval

The **new public field** would be one opaque, random-looking 256-bit commitment, represented as 64 lowercase hex characters. The Compute SHA is already public. Existing dispatch context still reveals workflow/route, actor and timing; this candidate does not conceal those facts. No receipt JSON, nonce, Store authority head, descriptor commit or private approval digest is a public input. Those remain private in the sidecar and caller context.

A fresh secret random nonce makes dictionary guessing of otherwise guessable pins impractical under ordinary SHA-256 assumptions. This is computational hiding, not encryption or a signature. Someone who learns the complete receipt can recompute and correlate its commitment. Reusing the exact receipt yields the same commitment, so repeated public submissions are linkable. A fresh nonce changes that identifier but **never** renews a consumed or expired permission. Private nonce entropy and secrecy matter; format validation cannot establish either.

## Trust and attacker model

The trust root is the **authorized owner's first-attempt manual dispatch and a trusted caller's exact approved creation/readback**, not possession of a token, the existence of a private ref, or a mathematically valid digest. A public commitment authenticates receipt bytes only relative to a separately trusted expected commitment. It proves neither the user's intent nor that the owner actually reviewed the receipt. This module intentionally reports `authorization_authenticated = False` and `production_activation = False`, including after successful verification.

- An unrelated public observer sees the opaque commitment and already public source/run context, not private receipt pins or nonce.
- A party able to alter a private sidecar or descriptor but unable to replace the approved public commitment cannot substitute different receipt bytes without detection (subject to SHA-256 security). Malformed, noncanonical or substituted receipts fail with one value-free error. Private Git object/ref integrity still needs the strict existing readers.
- A Store token holder can potentially read private material or alter accessible refs according to its actual permissions. The token supplies neither consent nor independent receipt provenance. Receipt generation by that token holder alone is insufficient; trusted approved creation/readback and owner dispatch must agree. A stolen read-capable token can defeat confidentiality of material it can read; the commitment does not remedy that.
- A malicious owner or compromised owner dispatch identity can approve/replace a commitment. A compromised trusted creator/caller or malicious reviewed Compute code can lie about validation, leak private values or bypass gates. This primitive does not protect against those trust-root failures. Source review, exact source identity, workflow/permissions enforcement and trusted execution remain necessary.
- A mutable ref lookup cannot supply both the receipt and its expected independent authority without a trusted dispatch commitment and approved provenance. Never trust a commitment fetched from the same untrusted location as the receipt.
- Private `repr` and value-free exceptions reduce accidental diagnostics, not all exfiltration. Returned canonical bytes, object fields, debugger locals, serialization and memory remain private and must not be logged. Verification uses `hmac.compare_digest` on validated fixed-length hex digests; this is not a claim that the entire parser/function is constant-time.

## Replay, failures and unresolved activation decisions

The receipt has no new execution grant, freshness window, budget, request ID or durable consumption ledger. Replaying the same valid receipt still verifies mathematically. Existing owner/manual/main/first-attempt identity, same-repository collector lock, exact current Store head and descriptor rechecks, runtime approval validity, request and credit limits, create-only claims, durable debit/provider guard, evidence retention and main advancement remain mandatory. A different nonce, descriptor or request ID cannot revive a spent grant. Occupied refs, changed heads, consumed claims, expired approvals, uncertain publication or unknown request outcomes stop without automatic retry or repair.

Before activation, decisions and work still required are: explicit approval to disclose this public commitment; exact final Compute source and merge; approved private authority/descriptor/sidecar placement and immutable readback protocol; final executing integration of the reviewed quiet sidecar/object readers; concrete one-shot scope and validity/budget/retention terms; complete hosted source/concurrency and unchanged runtime-gate binding; independent end-to-end review and synthetic verification. No live read, secret, permission expansion or activation is justified by this candidate.

## Local verification

Synthetic tests cover both routes, domain separation, field binding, strict schema/encoding and input bounds, context mismatches, redacted results, clean exception chains, and nonce/linkability behavior. They use no production credentials or data. Pure functions accept caller-supplied nonce bytes encoded as hex; production nonce generation and sidecar creation deliberately remain outside this candidate.

A separate optional local composition, `prepare_committed_authority` in the preflight module, can check the receipt commitment and independent route/Compute expectations before local materialization. That composition does not change this receipt primitive's trust model: it is not a hosted sidecar fetch, workflow binding, permission grant or production activation.

The workflow input and quiet sidecar/object readers are implemented, but neither workflow invokes them: both still stop at the deployment gate before private reads. Adding this interface does not activate production or create an execution approval.
